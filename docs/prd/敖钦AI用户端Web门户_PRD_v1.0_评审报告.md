# 📋 评审结论

## 总体判定

**结论：⚠️ 有条件通过**

> 本 PRD 结构完整、图表丰富、数据字典详尽，充分反映了 Stage A 原型阶段的真实状态。文档覆盖了全部 6+4 页面、13 JS 模块、28 项 sessionStorage Key，信息粒度达到可直接开发核对的程度。但由于当前为概念验证原型阶段，存在以下系统性待补充项：缺少正式用户故事、缺少加载/空/错误状态覆盖、缺少埋点方案、缺少隐私合规声明。以上重要项建议在进入 Stage B 正式开发前补齐。

---

## 通过条件与不可上线条件

### ✅ 通过条件（原型 Stage A）
满足以下条件可进入原型阶段开发/修改：
1. 模块间数据流和 sessionStorage Key 正确定义
2. 页面路由和依赖关系清晰
3. 智能体数据模型字段完整
4. 反馈→专家→工单全链路流程闭合并描述完整

### 🚫 不可上线条件（正式发布时）
存在以下任一条件，不可用于正式生产环境发布：
1. Mock 认证未替换为真实 IAM/SSO
2. 用户数据无后端持久化（当前 sessionStorage 仅原型用）
3. 隐私政策未更新
4. 缺少埋点方案导致核心指标不可追踪

## 各角色评审意见

### 👤 产品经理

**判定：有条件通过**

- **优势**：文档结构清晰，9 章体系覆盖完整，功能树和页面布局图直观，架构图和流程图丰富（20+ 图）。特别是"做/不做范围"和"原型限制说明"清晰，免去了后续的边界争议。
- **问题 1**：缺少正式用户故事。当前的模块描述偏功能和交互层面，缺乏从用户视角出发的场景描述。对齐团队时可能产生"为什么要做这个功能"的疑问。
- **问题 2**：优先级标注只在验收标准表中出现，功能清单层面缺少统一的 P0/P1/P2 标记，不便于团队判断各模块的迭代优先级。
- **问题 3**：Banner 点击行为定义过于模糊，@4.4："点击联动分类 Tab" 未说明具体跳转逻辑。

### 👨‍💻 研发工程师

**判定：有条件通过**

**开发周期评估（原型 Stage B 首次正式开发粗估）**：
- 前端：15~25 人/天（6 主页面 + 4 子页面 + 13 JS 模块的重构与 API 对接）
- 后端：20~35 人/天（认证服务、智能体 CRUD、知识库检索、反馈工单流）
- 联调：5~10 人/天
- **合计粗估：40~70 人/天**（不包含海能推理网关对接）

- **优势**：sessionStorage Key 表非常详尽（28 项），这对后端 API 设计和数据契约对齐极有帮助。Agent 数据模型 20 个字段全部列出，可直接作为 API Schema 参考。
- **问题 1**：当前所有数据流基于 sessionStorage，进入 Stage B 后需要全部替换为 API。PRD 7.1 给出了映射表，但缺少 API 的请求/响应结构定义（当前阶段可接受，但建议标注待补充）。
- **问题 2**：并发场景未考虑——如果用户在两个 Tab 中同时操作同一智能体的历史会话，sessionStorage 无法同步。这是一个已知的原型限制，建议在 8.4 补充说明。
- **问题 3**：忘记密码流程中的验证码逻辑完全 Mock（固定 123456），正式实现时需补充验证码发送频率限制、有效期、重试次数等约束。

### 🧪 测试工程师

**判定：有条件通过**

- **优势**：9.5 验收标准表给出了 14 个可执行的验收项，覆盖 P0 核心流程。字段校验规则（邮箱格式、密码长度、笔记字数限制等）定义清晰。
- **问题 1**：缺少异常路径的专门测试用例。例如：登录时网络中断、发送消息时 session 过期、知识库加载失败、反馈提交时图片过大等场景未在 4.3-4.6 的表格中覆盖。
- **问题 2**：边界条件未充分定义：消息输入框 2000 字的截断行为是什么？笔记标题最长多少字？附件最大 5MB（反馈截图）但 Composer 的文件上传有无大小限制？建议在 8.3/8.4 补充边界值表。
- **问题 3**：状态覆盖方面，4.5 的个人智能体状态只有 draft → submitted 一条路径，缺少 submitted → rejected / draft → deleted / submitted → listed 等完整状态机。

### 🎨 UI/UX 设计师

**判定：有条件通过**

**设计周期评估**：
- 交互稿：3~5 人/天（已有 Figma 原型 376 系列，主要是补全缺失的 Frame）
- 视觉稿：5~8 人/天（对齐设计 Token，确保 4 个 DeepSeek 模型名显示符合 ADR-015 v5）
- 总计：8~13 人/天

- **优势**：4.3 页面布局图准确标注了侧栏/顶栏/对话区/Composer 四大区域和交互组件，设计 Token（色/字/间距）已给出 CSS 变量级定义，可直接作为开发基准。
- **问题 1**：多处状态设计缺失——智能体广场的"卡片网格加载中"、Composer 附件上传的进度（当前是瞬间完成）、笔记列表为空时的引导图、专家工作台筛选结果为空的提示。
- **问题 2**：模型选择器的 4 个 DeepSeek 全名较长，在顶栏有限宽度内的显示策略（截断/换行/省略）未讨论。
- **问题 3**：Composer 底栏的 toolbar 按钮（深度思考/指定知识库/Skills）在移动端/窄屏场景下的布局策略未说明（当前仅考虑桌面）。

### 📊 运营

**判定：有条件通过**

- **优势**：反馈→专家→工单全链路流程描述完整（6.3 的 6 参与者序列图），路由分类表清晰。智能体广场的数据供给方式（UserAgentResolver 4 路聚合）和权限过滤规则明确。
- **问题 1**：全篇未提及埋点方案。运营无法追踪核心指标：日活（DAU）、消息发送量、反馈率、智能体使用分布、专家任务完成率。建议补充一份最低埋点数据集。
- **问题 2**：无灰度策略说明。新功能上线是全量发布还是灰度？智能体广场的 Banner 推荐内容能否由运营配置？
- **问题 3**：专家工作台的 SLA 未定义——P0 任务的响应时效要求是什么？超时后的升级/告警机制是什么？

### ⚖️ 法务/合规

**判定：有条件通过**

- **优势**：8.3 安全要求涵盖了 XSS 防护（escapeHtml）、同源策略、登录门禁等基础措施。
- **问题 1**：用户反馈提交时会收集"截图（图片文件）"，这属于用户生成内容（UGC）。PRD 未说明图片的处理方式（是否上传服务器？存储多久？谁可以查看？）。
- **问题 2**：个人笔记存储在 sessionStorage（Tab 关闭即消失），但"个人智能体提交审核"会将草稿写入 `proto_ops_v11_agents`（原型阶段仍在 sessionStorage，但正式阶段会进入运营端数据库）。PRD 未说明运营端查看用户个人智能体的权限边界。
- **问题 3**：收集的企业邮箱地址（`proto_user_session.email`）用于登录标识，但未见隐私政策引用或用户同意机制。建议在 login.html 增加隐私政策链接。
